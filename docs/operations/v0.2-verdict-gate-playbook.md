# goat-client v0.2 verdict-gate operator playbook

> **Audience.** The captain / release operator who closes the v0.2.0
> verdict gate and decides when to cut `goat-client-v0.2.0`. Per
> [ADR 0840 Amendment 2026-05-13](https://github.com/dlf-dds/DesertBreadBird/blob/main/docs/adr/0840-goat-client-cross-platform-daemon-gui.md)
> and [implementation-plan Block 76N–Q](https://github.com/dlf-dds/DesertBreadBird/blob/main/docs/project/implementation-plan.md#block-76)
> the v0.2 ship gate is seven items (a)–(g). Three close from CI +
> the parity audit; this doc walks the four that require an
> operator on real hardware: **(b)**, **(c)**, **(e)**, **(g)**.

## How to use this doc

For each gate below:

1. Run the **pre-flight checklist** — verify your environment matches
   what the gate measures.
2. Run the **test sequence** in order. Each step has a "pass" string
   that must appear; "fail" means the gate is not closed.
3. Capture **evidence** as you go. Evidence destination is the
   per-gate "where evidence lands" subsection — usually a comment on
   the GitHub Release draft, an entry in `active-work.yaml` in
   goat-trunk, or a screenshot in the goat-trunk `docs/evidence/`
   directory.
4. Mark the gate closed in this doc by editing the corresponding
   line in the **verdict-gate map** of
   [`CHANGELOG.md`](../../CHANGELOG.md) `[0.2.0]` section from ⚠ to
   ✅ in the same PR that cuts the tag.

The captain is the final arbiter for every gate. The intent of this
doc is to make the captain's "is gate X closed?" answer mechanically
verifiable rather than vibe-based.

## (a) regression bar — closed from CI

Listed here for completeness only. `wg-cp0-only` mode must remain
byte-identical to v0.1.x behaviour on every platform. The closure
mechanism is:

- `internal/daemon/three_mode_smoke_test.go::TestThreeMode_WGCP0Only`
  exercises the `wg-cp0-only` path against in-process fakes on every
  PR.
- `internal/innermesh/innermesh.go::New()` constructs `*Netbird` post-
  M5, but `Connect` short-circuits when the mode is `wg-cp0-only` —
  the inner-mesh path is never reached. Captured by
  `TestDaemonConnect_WGCP0Only_DoesNotConstructMesh`.
- The cross-platform PR-gate matrix from v0.1.2 (GAP #3) runs
  `go test -race` on every PR against linux/amd64 / linux/arm64 /
  darwin/arm64 / windows/amd64 + builds (no race) on windows/arm64.

**No operator action.** If any of the above start failing on main,
roll back the offending PR; do not tag.

## (b) `combined` on ≥3 desktop installs

**What this measures.** That the three-mode triad lands with both
tunnels actively passing peer-reach traffic on real desktop hardware,
not just in-process smoke fakes.

### Pre-flight checklist

- [ ] PR #50 (M5 `New()` flip) merged on `main` and at least one
      green tag-build off `main` has produced cosign-signed archives.
- [ ] PR #53 (DeviceID composition) merged — peer name in mgmt UI
      will read `"<bundle> (<host hostname>)"` on desktop and the
      identity has to be inspectable for the evidence step.
- [ ] Three distinct desktop hosts available. Distribution-cover at
      least two OSes: e.g. one Linux + one macOS + one Windows; or
      two Linux + one macOS. Targets must include a mix of
      `amd64` + `arm64` if possible.
- [ ] netbird mgmt server reachable from each desktop's outbound
      network path. For `combined` mode the inner-mesh leg goes
      direct mgmt — this is NOT yet over the Block 80 crutch
      (verdict-gate (d), deferred).
- [ ] Three distinct enrollment bundles, one per host, each with:
      - `inner_mesh_setup.management_url` pointing at the netbird
        mgmt server.
      - `inner_mesh_setup.setup_key` valid for at least the
        duration of the test.
      - `device_id` distinct per bundle (use a recognisable shape:
        `desktop-b-host1`, `desktop-b-host2`, `desktop-b-host3`).
- [ ] Operator has shell access (or screen-share / remote desktop)
      to each host for log capture.

### Test sequence

For **each** of the three hosts, in order:

1. **Install the v0.2.0-rc archive.** Use the cosign-verify recipe
   from [`README.md` → "Verifying release artifacts"](../../README.md#verifying-release-artifacts);
   the binary must be the same one the eventual release ships.
   Captain: this is the gate where the v0.2.0-rc tag earns its
   keep. Pre-tag the same SHA from `main` as
   `goat-client-v0.2.0-rc1` (or `-rc2` etc) so the tag-build
   workflow produces archives.

2. **Pick `combined` mode at install time.**
   - Linux: `GOAT_MODE=combined apt install ./goat-client_*.deb`
     (Debian/Ubuntu) or the rpm equivalent.
   - macOS: install the `.dmg` then `defaults write ~/Library/...
     mode combined` per the GUI's first-run flow (the bundle-import
     dialog asks).
   - Windows: install the `.msi` then pick `combined` in the GUI's
     first-run flow.

3. **Import the per-host bundle.** Via the Fyne GUI on
   desktop with a windowing system, or via the daemon socket on a
   headless host (see (e) playbook). Confirm the GUI's status pane
   renders both stacked cards: outer (wg-cp0) on top, inner
   (netbird) below.

4. **Connect.** Click the Fyne Connect button (or invoke
   `connect` over IPC).

5. **Verify the outer leg.** Expected log line:
   `goat-clientd: wg-cp0 up to <relay-endpoint>` and the outer
   statusCard transitions to `connected` (brand green dot). Ping a
   known wg-cp0 mesh IP (e.g. `198.18.0.1`):
   ```
   ping -c 3 198.18.0.1
   # Pass: 3 packets, 0% loss
   ```

6. **Verify the inner leg.** Expected log line:
   `goat-clientd: inner-mesh up` and the inner statusCard transitions
   to `connected`. Confirm in the netbird mgmt UI that this host
   appears as a peer with name `"<bundle.device_id> (<hostname>)"`
   (e.g. `"desktop-b-host1 (ops-laptop-04)"`). Peer state must be
   `online`. **This is the load-bearing wire-side observation** —
   without it, you have not closed (b) for this host; you have only
   confirmed the outer leg.

7. **Verify inner-mesh peer reach.** Identify another peer in the
   netbird mgmt UI — preferably one of the OTHER two test hosts
   from this gate run, OR a known-good fixture peer the operator
   has on the mgmt server. Ping its inner-mesh IP (typically in the
   netbird-assigned `100.64.0.0/10` range):
   ```
   ping -c 3 <other-peer-inner-ip>
   # Pass: 3 packets, 0% loss
   ```
   If pinging another test host: do this **after** that host has
   also completed step 6, so both sides are registered.

8. **Capture evidence.** For this host:
   - Save the `journalctl -u goat-clientd.service --since "10
     minutes ago"` output to
     `evidence/v0.2.0/b-desktop-<hostnum>-<os>.log`.
   - Screenshot the netbird mgmt UI peer list with this host's peer
     row visible.
   - Screenshot the Fyne status pane in `combined` mode with both
     cards `connected`.

### Pass criteria

- [ ] 3 hosts each complete steps 5 + 6 + 7 without manual workaround.
- [ ] Inner-mesh peer reach (step 7) confirmed on each host — not
      just outer wg-cp0 reach.
- [ ] At least one host's inner-mesh peer reach goes to ANOTHER host
      from this gate run (so peer-to-peer through real mgmt-server-
      negotiated keys is observed, not just star-from-mgmt-fixture).

### Fail modes to watch for

- **Inner statusCard stuck at `connecting`** — Mesh.Connect is
  reaching mgmt but mgmt is rejecting Login or the device's
  `MobileCert` is missing when mgmt is configured to require it.
  Check `goat-clientd` logs for `embed.Client: login:` lines.
- **Inner statusCard at `error` immediately** — mgmt URL unreachable
  or DNS not resolving the mgmt hostname. Pre-flight bullet 4.
- **Peer name in mgmt UI is just the hostname (no bundle prefix)** —
  PR #53 not on main, or the bundle's `device_id` is empty.

### Where evidence lands

A new comment on the goat-trunk active-work entry for v0.2.0
release-prep, with the three log files + screenshots attached. Or
goat-trunk `docs/evidence/v0.2.0-gate-b/` directory if active-work
has rolled forward by the time this runs.

## (c) `combined` on ≥1 iOS + ≥1 Android device

**What this measures.** That the mobile triad UI (PR #36) +
SDK-bridge (PR #40) + DeviceID composition (PR #53) work end-to-end
on real handsets reaching real mgmt, not on simulator/emulator
fixtures.

### Pre-flight checklist

- [ ] (b) is green, OR there's a strong reason it's safe to run (c)
      without (b) — typically (b) goes first because desktop
      regressions are easier to triage. The captain decides.
- [ ] PR #50 + PR #53 merged on main.
- [ ] iOS TestFlight build of the v0.2.0-rc shipped via PR #44's
      pipeline. Build available in TestFlight to at least one
      tester (the operator).
- [ ] Android Play Internal-track build of the v0.2.0-rc shipped
      via PR #44's pipeline. Build available in the internal track
      to at least one tester (the operator).
- [ ] At least one iPhone (iOS 16+; the project's deployment target
      per PR #28) registered to the TestFlight tester pool.
- [ ] At least one Android handset (minSdk 24, compileSdk 35) in
      the Internal-track tester pool.
- [ ] Two distinct enrollment bundles, one per device. Same
      `inner_mesh_setup` shape as (b), plus optional `mobile_cert`
      — only consumed once Block 80 is live (verdict-gate (d)), so
      for (c) the `mobile_cert` field can be absent.
- [ ] netbird mgmt server reachable from each handset's outbound
      network — typically over cellular or office Wi-Fi.

### Test sequence

For **each** of the two devices, in order:

1. **Install the TestFlight / Play Internal build.** iOS: tap the
   TestFlight link, install. Android: open the Play Internal-track
   invite, install.

2. **Open the goat-client app.** First-run flow asks for bundle
   import + mode pick.

3. **Import the per-device bundle.** Use the document picker (iOS
   `UIDocumentPicker`) or Storage Access Framework (Android) to
   pick the `.cbor` file. The app should render the
   `BundleCapabilities` strip (PR #40 surface): `wg_cp0: true`,
   `inner_mesh: true`, `has_mobile_cert:` per-bundle.

4. **Pick `combined` mode in the mode-selector card.** Mode persists
   to App Group UserDefaults (iOS) / SharedPreferences (Android);
   stays selected across app restarts.

5. **Tap Connect.** The OS prompts for VPN configuration consent
   (`NETunnelProviderManager.saveToPreferences` on iOS;
   `VpnService.prepare` on Android). Approve.

6. **Verify the outer leg.** Outer `TunnelStatusCard` transitions
   to `connected`. Ping a wg-cp0 mesh IP via the OS's network
   diagnostics (iOS Settings → Wi-Fi → connected network → ping
   tool, or use an in-app diagnostics surface if one is wired; for
   Android use `adb shell ping` against the connected handset).

7. **Verify the inner leg.** Inner `TunnelStatusCard` transitions
   to `connected`. Confirm in the netbird mgmt UI that the device
   appears as a peer with name `"<bundle.device_id> (<device-
   reported>)"` — on iOS the device-reported half is
   `UIDevice.current.name` (note: on iOS 16+ without the
   user-assigned-device-name entitlement this generalises to just
   `"iPhone"`); on Android it's `"<Build.MANUFACTURER>
   <Build.MODEL>"`.

8. **Verify inner-mesh peer reach.** Either (a) ping a known-good
   fixture peer's inner IP from within the handset (use an
   in-app diagnostics ping or a third-party ping app), OR (b)
   confirm the OTHER test device (after it completes step 7) appears
   in the netbird mgmt UI peer list with `online` state AND reach
   the inner IP from the desktop test hosts of gate (b).

9. **Stress: mode switch.** Change mode from `combined` to
   `wg-cp0-only` in the GUI. Confirm the extension restarts
   (PacketTunnelProvider `stopTunnel` → reload → `startTunnel` on
   iOS; foreground-service `ACTION_STOP` → debounce → `ACTION_START`
   on Android). Confirm the inner card transitions to `disabled`
   and the outer card remains `connected`. Switch back to
   `combined`; confirm inner returns to `connected`. This is the
   gate's confirmation of the mobile-platform restart contract from
   `docs/parity-audit-desktop-vs-mobile.md` §2.

10. **Stress: network change.** Toggle airplane mode on for 5
    seconds then off (or switch from Wi-Fi to cellular). Confirm
    both cards reconnect within 30 seconds without manual
    intervention. Per the parity-audit's mobile-platform behavioural
    contract.

11. **Capture evidence.** For this device:
    - Export the goat-client log file via the app's diagnostics
      sheet (iOS: Files app → on-device folder; Android: app's
      external storage path).
    - Screenshot the netbird mgmt UI peer list showing this device's
      peer row with the composed name.
    - Screenshot the in-app status pane in `combined` mode with both
      cards `connected`.

### Pass criteria

- [ ] 1 iOS + 1 Android complete steps 6 + 7 + 8.
- [ ] Mode switch (step 9) and network change (step 10) succeed
      without manual intervention.
- [ ] Composed peer name in mgmt UI shows both halves of identity on
      both devices.

### Fail modes to watch for

- **`NETunnelProviderManager.loadAllFromPreferences` fails with
  "IPC failed"** — iOS Simulator only; should not happen on real
  device. If it does, the build isn't signed for the device's UDID;
  re-verify PR #46's Distribution-profile config landed.
- **Android `VpnService.prepare` returns null then `onRevoke` fires
  immediately** — another VPN client owns the system VPN slot.
  Single VPN on Android per the platform; uninstall the
  conflicting client.
- **Inner-mesh peer never appears in mgmt UI** — the gomobile-bound
  `embed.Client` isn't reaching mgmt. Pull the goat-client log via
  the app's diagnostics export and grep for `embed.Client: login:`
  / `embed.Client: sync:` lines.
- **Peer name in mgmt UI shows just `"iPhone"` with no bundle
  prefix** — bundle's `device_id` is empty. Re-mint with a non-
  empty `device_id`.

### Where evidence lands

Same destination as (b): goat-trunk active-work or
`docs/evidence/v0.2.0-gate-c/`. Include the .ipa / .aab build
metadata (TestFlight build number, Play Internal version code) so
the captain can reproduce the exact binary that closed the gate.

## (e) headless on a single-Orin site

**What this measures.** That the headless variant (PR #37,
`goat-client-headless` package) installs in ≤5 min on a fresh
Orin-class site, survives reboot, and co-resides cleanly with the
Block 61 snitch probe.

### Pre-flight checklist

- [ ] PR #50 merged on main; v0.2.0-rc tag has built the
      `goat-client-headless_*.deb` / `goat-client-headless-*.rpm`
      archives.
- [ ] One Orin-class site available (NVIDIA Jetson Orin, or any
      arm64 Linux box that approximates one). The pivotal traits
      are: arm64, headless (no GUI), systemd-init, restricted
      outbound (typical Orin field deployments).
- [ ] Operator has SSH-as-root (or passwordless sudo) to the box.
- [ ] One enrollment bundle minted for this box, with the
      operator's mode decision baked into how the operator invokes
      the install (`GOAT_MODE=combined` is the recommended default).
- [ ] [`docs/operations/goat-client-headless-bringup.md`](goat-client-headless-bringup.md)
      is reviewed; this gate is the runbook's first real-world
      exercise.

### Test sequence

1. **Time-start the install.** Note wall-clock start.

2. **Run the bringup runbook end-to-end** per
   [`goat-client-headless-bringup.md`](goat-client-headless-bringup.md).
   Steps 1–7 cover transfer + install + bundle-import + reachability
   verification.

3. **Time-stop the install.** Note wall-clock at the first
   successful ping in runbook step 7. **Pass: total ≤5 minutes from
   step 1.** This is the runbook's stated budget and the verdict-
   gate's pass criterion.

4. **Reboot.** `systemctl reboot`. Wait 30s for the box to come
   back. SSH back in. Confirm:
   ```
   systemctl is-active goat-clientd-headless.service
   # Pass: active
   journalctl -u goat-clientd-headless.service --since "1 minute ago" | grep -E 'bundle imported|up to|inner-mesh up'
   # Pass: lines present per the configured mode
   ```

5. **Snitch co-residency.** Install (or confirm pre-installed) the
   Block 61 snitch probe on the same box. The runbook calls out
   "snitch first, then goat-client-headless" as the install order —
   but for verdict-gate (e), the order is whichever the test
   started with. Confirm:
   - Both daemons run side-by-side without conflicting on
     `/run/goat-client/ipc.sock` vs snitch's IPC path.
   - Snitch's next cycle includes goat-client's outer wg-cp0
     interface in its observation set.
   - Snitch's `getLastReport` (over its own IPC) shows the
     goat-client peer-reach measurements per snitch's existing v0.2
     probe shape (Block 61H).

6. **Mode switch.** Issue a `setMode` over IPC per the runbook's
   "Switching mode after install" section. Verify the live mode
   switch happens in ≤30s.

7. **Capture evidence.** Save:
   - `journalctl -u goat-clientd-headless.service --since "1 hour
     ago"` to `evidence/v0.2.0/e-orin-<hostname>.log`.
   - Output of `socat - UNIX-CONNECT:/run/goat-client/ipc.sock`
     `getStatus` call.
   - Snitch's `getLastReport` JSON capturing the co-residency
     observation.
   - Wall-clock measurement of step 3 (total install time).

### Pass criteria

- [ ] Total install time ≤5 minutes (step 3).
- [ ] Reboot-survives (step 4) without manual intervention.
- [ ] Snitch co-residency (step 5) clean — both daemons live, snitch
      observes goat-client's interface.
- [ ] Live mode-switch (step 6) within 30s budget.

### Fail modes to watch for

- **`systemctl status goat-clientd-headless.service` shows
  `degraded`** — usually CAP_NET_ADMIN sandbox fighting a kernel
  without WG support. Runbook's "Common pitfalls" section covers
  this. Not a (e) blocker unless the userspace-WG fallback also
  fails.
- **Install >5 min because of `apt-get update` slowness** — that's
  the test box's package mirror, not goat-client. Note as a caveat
  in evidence but doesn't fail the gate; redo from a host with a
  warm mirror cache.
- **Snitch sees goat-client's interface but not its peer reach** —
  snitch probe needs a refresh cycle; wait one cycle interval and
  re-check before failing.

### Where evidence lands

Same as (b) + (c).

## (g) TestFlight + Play Internal submission

**What this measures.** That the operator-fired mobile release path
through Apple + Google review actually fires — i.e. that one
TestFlight build and one Play Internal-track build are live and
have passed review acceptance, not merely sitting in the upload
queue.

### Pre-flight checklist

- [ ] PR #44 (mobile release-signing pipelines), PR #46 (iOS signing
      fix), PR #47 (ASC API client + tester CLI) all on main.
- [ ] Apple Developer Program membership active.
- [ ] App Store Connect API key configured in CI secrets
      (`APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`,
      `APP_STORE_CONNECT_PRIVATE_KEY` — see PR #47).
- [ ] Google Play developer account active.
- [ ] Play Console service-account JSON configured in CI secrets.
- [ ] App listing pages exist in App Store Connect + Play Console
      with required metadata (privacy policy URL, screenshots, app
      description). This is a one-time setup; the gate doesn't
      cover initial-listing creation, just the release upload.
- [ ] At least one external email registered as a TestFlight tester
      and as a Play Internal-track tester (the operator counts).

### Test sequence

1. **Cut the v0.2.0-rc tag.** Push `goat-client-v0.2.0-rc1` (or
   later -rc) to origin. This triggers the release.yml workflow's
   mobile-release path (PR #44).

2. **iOS — wait for TestFlight processing.** The pipeline uploads
   the `.ipa` to App Store Connect via `xcrun altool` /
   `upload-package`. ASC takes 10–30 min to process the build; it
   moves through `Processing` → `Ready to Submit` → operator-marks
   for testing. Per the ASC API tester CLI (PR #47),
   ```
   mobile/scripts/asc-tester-cli add-build \
       --version 0.2.0 \
       --build <build-number> \
       --testers operator@example.com
   ```
   adds the operator to the build's tester pool without going
   through the ASC web UI.

3. **iOS — install the TestFlight build on the operator's device.**
   TestFlight app on the iPhone shows the build; tap Install. The
   build must launch without crashing on first-run before the
   `combined` mode flow exercises the bundle-import dialog.

4. **iOS — confirm review acceptance.** For Internal Testing /
   TestFlight, Apple's review pass is automated for build
   processing only — no manual reviewer involvement is required
   for internal-only TestFlight access. **Pass criterion:** the
   build is `Internal Testing` state in ASC and installable from
   TestFlight without "Beta App Review required" gating.

5. **Android — wait for Play Internal processing.** The pipeline
   uploads the `.aab` to the Play Console Internal track via the
   service account. Processing is typically faster than ASC
   (5–15 min). The build moves through `In review` → `Available to
   testers`.

6. **Android — install the Play Internal build.** From the
   operator's Android handset, accept the Internal-track invite
   email, follow the Play Store link, install. Build must launch
   without crashing.

7. **Capture evidence.** For each store:
   - Screenshot of the build's state page in ASC / Play Console.
   - Screenshot of the build installed on the operator's device
     (from TestFlight app / Play Store app).
   - Build number + version code metadata.

### Pass criteria

- [ ] iOS TestFlight build is `Internal Testing` and installable
      (step 4).
- [ ] Android Play Internal-track build is `Available to testers`
      and installable (step 6).
- [ ] Both builds launch without crashing on first-run.

### Fail modes to watch for

- **`xcrun altool: error 1191: provisioning profile doesn't include
  the currently selected device`** — PR #46's Distribution-profile
  config didn't land or has drifted. Re-verify the project's
  Release configuration is using the Distribution profile, not
  Development.
- **Play Console `INVALID_VERSION_CODE`** — versionCode reuse. PR #45
  bumped to versionCode 2; v0.2.0-rc must bump again. Add this to
  the "files to bump" list when cutting the v0.2.0 tag.
- **TestFlight build stuck in `Processing` >2 hours** — ASC backlog.
  Not a (g) blocker; note as a caveat and recheck the next day.
- **Build crashes on first-run** — this is a code regression, not a
  gate-(g) issue. Roll back the offending PR and re-run from the
  rc-tag step.

### Where evidence lands

Captain attaches the screenshots to the v0.2.0 GitHub Release draft
as the closure narrative for (g). Build numbers + version codes go
in the release notes so the same binaries are reproducible.

## Closing the gate

When all four operator-fired gates above show pass:

1. Update the verdict-gate map table in
   [`CHANGELOG.md`](../../CHANGELOG.md) `[0.2.0]` section — flip ⚠
   to ✅ for (b), (c), (e), (g). Leave (d) as ⛔ blocked.
2. Rename the `[0.2.0] — UNRELEASED` heading to `[0.2.0] — YYYY-MM-DD`
   in the same edit.
3. Update CHANGELOG footer compare-links to point at the new tag.
4. Bump the "files to bump" set per the v0.2.0-release-prep PR's
   appendix (also linked from `HANDOFF.md`).
5. Tag `goat-client-v0.2.0` on the merge commit.
6. The tag-build workflow takes it from there.
